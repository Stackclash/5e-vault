# Editing templates

Templates live in `z_Templates/Templater/`. Note-creating templates share one pattern:

```javascript
const init = tp.user.templateInit()      // z_Scripts/Templater/templateInit.js
const fields = tp.user.formFields()      // z_Scripts/Templater/formFields.js
const { dataview, modalForm, config, path } = init.getPlugins(tp, ['requiredConfigKey'])
const data = await init.openForm(modalForm, { title: "...", fields: [...] })
await init.moveFile(tp, config.locations.myPath, data.name)
```

`config` is `1. DM Toolkit/Configuration.md` frontmatter; `config.locations.*` are folder paths.

## The note skeleton (04 Expansion §2)

Entity templates (NPC, Location, Shop, World, Faction, Item, Deity, Creature, Quest) are generated by `z_Extra/migration/c6-templates.js`; edit the generator and rerun it rather than hand-editing one template. Each body is, top to bottom:

1. **Header**: `dv.view('views/entityHeader')`: breadcrumb, images, name, `pronounced`, state chips (Meta Bind inputs for the `chip: true` fields), and the knowledge badge with the Revealed toggle. Then an **Edit all** button (`z_Scripts/Meta Bind/editAll.js`).
2. **Gist strip**: a `> [!gist]` callout holding the `gist` input.
3. **Infobox**: the ITS `[!infobox]`; each row renders through `dv.view('utils/noteFieldInput', {current, field})` so the input type and option list come from Configuration.
4. **Tab box**: `<% tp.file.include("[[z_Templates/Partials/Tabs - <Type>]]") %>`. Partials are generated by `z_Extra/migration/c8-partials.js`. The tab select sits in a `meta-bind` block bound to `memory^tab` (switching tabs writes nothing); each panel is one child callout of `[!tabbed-box]` (10 at most: the snippet handles 8, `Custom Styles.css` adds 9 and 10). Keep each panel short: a very tall panel whose content loads late gets unloaded by reading view and makes Live Preview jump to the top. Every tab box includes `Partials/Player-Facing` (Revealed, Public name, Also show, summary, FactsTable), except Player Character, which includes `Partials/Player-Facing - No Reveal` (summary, FactsTable), and Creature, which has no Player-Facing tab. Meta Bind rejects a single quote in an unquoted argument, so tab names use the typographic apostrophe (`What’s Here`).
5. **Stats tab** (NPC, creature): the `statblock` block lives in a tab. T12 (2026-11-16): Fantasy Statblocks and the Initiative Tracker still read it; `#^statblock` embeds do not resolve inside callouts, so other notes show a stat block with a `statblock` block holding `monster: <Name>`.

**DM Notes live in the DM tab** (DM, 2026-11-16): the last lines of the tab box are `> > ## DM Notes`, and DM prose goes below that heading with the `> > ` prefix; the **Edit DM Notes** button (`z_Scripts/Meta Bind/editSection.js`) opens the section as plain markdown in a modal and writes the prefix back. Imported module text (from `monster.txt`) goes in a `## Source` section after the tabs.

**Colour:** `[!player]` (green) holds player-facing content; `[!dm]` (red) holds DM-only content. Nothing else uses those colours.

**One field list per type.** `Configuration.note_fields` lists every editable flat field per type: `{field, input, enum, source, tab, chip, bulk, per_party, label}`. The infobox rows, header chips, Edit all, and the Bases edit views (C10) all read it. Option lists come from `Configuration.enums` (or a top-level list of `{name}` such as `settlement_wealth`), never from hard-coded `option(...)` lists. The lint rule `note-fields` checks each entry. Adding a field: add it to the schema reference, to `note_fields`, and to the template frontmatter.

**Editing rules (Q1–Q7):** anything shown is editable where it is shown (Q1); every header has Edit all (Q2); long text fields get a pop-out button (`popOutEditor.js`), because Meta Bind text areas can't auto-grow here (Q4, T10); lists use an Add button above the table, with reorder and delete per row (Q6); a per-party value can be cleared with its × button.

**Creation forms** ask only name, gist, and location/parent (and level for locations). Everything else is filled in the note. `templateInit.moveFile` creates the target folder if it does not exist yet.

## The NPC mirror

`z_Extra/ttrpg-convert/templates/monster.txt` has an `{#if resource.isNpc}` branch that mirrors `z_Templates/Templater/World Building/NPC.md`, so bulk-imported NPCs match hand-made ones.

**Any edit to NPC.md's frontmatter keys, infobox, sections, inputs, or buttons needs the equivalent edit in that branch.** Translate, do not paste: Qute uses `{#if}`, `{#for}`, `{resource.field}`; literal braces in the output are escaped as `\{` and `\}`. Say in your summary that both files changed. No other template has a mirror.

## Meta Bind array buttons

Use the dispatcher for any button that edits a frontmatter array:

```yaml
actions:
  - type: js
    file: z_Scripts/Meta Bind/arrayActions.js
    args: { action: add, field: items }      # add | remove | moveUp | moveDown; index for all but add
```

The older `addItem.js`, `removeItem.js`, `moveUp.js`, `moveDown.js` are still referenced by existing notes; do not use them in new buttons and do not delete them.

## Scripts by runtime

| Runtime | Path |
|---|---|
| Datacore (JSX) | `z_Scripts/Datacore/` |
| Dataview views | `z_Scripts/Dataview/views/` (called as `dv.view("views/…")`) |
| Dataview helpers | `z_Scripts/Dataview/utils/`, `data/`, `render/` |
| Node CLI | `z_Scripts/JS/` |
| Meta Bind | `z_Scripts/Meta Bind/` |
| Templater helpers | `z_Scripts/Templater/` |
| Agent index and lint | `.claude/skills/vault-lint/scripts/` |

A field rename is not done until every script, Base, and template that reads the field is updated. Grep `z_Scripts`, `z_Bases`, `z_Templates`, and note bodies for the old name first.
